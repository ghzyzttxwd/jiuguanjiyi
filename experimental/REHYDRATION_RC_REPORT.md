# Variable Archive Bridge 冷档案重激活 / Rehydration RC1

## 要解决的问题
冷归档以后，一个旧人物、旧武学或旧世界可能在后续剧情中重新成为活跃对象。此时模型/MVU有可能先重新创建一个**不完整的新热节点**。

最危险的处理方式是直接把旧冷档案整块覆盖回来：这样会把“刚发生的新变化”抹掉。

因此重激活必须遵循：

> 冷档案负责补历史缺失字段；当前热变量负责当前事实，发生冲突时热变量优先。

## RC1 合并规则
### 对象节点
若冷档案与当前热节点都是普通对象：
- 先以冷档案作为历史基底；
- 递归补齐当前热节点没有的旧字段；
- 当前热节点已经存在的字段一律覆盖冷值；
- 嵌套对象同样执行“冷补缺、热覆盖”；
- `__proto__` / `prototype` / `constructor` 永久排除，避免原型污染。

示例：

冷档案：
```json
{
  "身份": "轮回者",
  "关系": { "好感": 80, "信任": 75, "状态": "盟友" },
  "装备": { "武器": "长剑" }
}
```

后来新热节点：
```json
{
  "关系": { "好感": 88, "状态": "同行" },
  "当前地点": "主神广场"
}
```

计划合并结果：
```json
{
  "身份": "轮回者",
  "关系": { "好感": 88, "信任": 75, "状态": "同行" },
  "装备": { "武器": "长剑" },
  "当前地点": "主神广场"
}
```

### 数组 / 标量节点
数组和标量视为当前状态原子值：
- 只要热节点已经重新出现，就以热值为准；
- 不把旧数组与新数组机械拼接；
- 不用旧标量覆盖新标量。

## 三种计划类型
`rehydration_core.js` 当前只负责计算，不负责写入：

1. `mark-restored`
   - 冷档案与新热节点完全一致；
   - 未来只需把冷档案状态关闭，不需要改MVU。

2. `merge-hot-over-cold`
   - 冷/热均为对象且内容不同；
   - 生成“冷补缺、热覆盖”的完整合并结果。

3. `keep-hot-mark-restored`
   - 新热节点为数组或标量；
   - 当前热值完全保留，旧冷值不覆盖。

## 只读候选 UI
`rehydration_safe.js` 目前只有一个按钮：**只读检查重激活**。

它会：
- 刷新读取当前MVU；
- 找出 `status=archived` 但同 pointer 已重新出现在热变量中的档案；
- 显示合并计划、差异计数与合并后的预览；
- 不修改MVU；
- 不修改IndexedDB；
- 不调用 `archiveChild()`；
- 不调用 `restoreArchive()`；
- 不调用 `replaceMvuData()`。

因此 RC1 只能观察和验证规则，不能真正执行重激活合并。

## 和“自动召回”的分工
最终应严格区分三种情况：

1. **只是聊天提到旧对象**
   - 只走冷档案 Prompt 召回；
   - 不恢复成热变量。

2. **旧对象重新成为真正的活跃状态**
   - 可恢复/重激活为热变量。

3. **MVU已经先创建了不完整的新热节点**
   - 走 Rehydration 合并；
   - 不允许旧冷档案粗暴覆盖新状态。

这能避免“随便提一句旧人物，整个档案又被塞回MVU”的反复抖动。

## 自动化测试
当前测试覆盖：
- 嵌套对象冷补缺、热覆盖；
- 数组/标量热值优先；
- 完全相同节点判为 `mark-restored`；
- 已恢复/不存在热节点不产生计划；
- JSON Pointer 特殊字符转义；
- 原型污染键拦截；
- 同 pointer 去重；
- 每轮计划数量限制；
- 端到端生命周期：冷归档 → Prompt召回 → 旧宏冲突让路 → 热节点重建 → 合并计划 → 热节点存在后停止重复召回；
- 5001 条冷档案规模下仍能找到目标档案。

## 下一阶段
在不接入自动写入的前提下，先冻结**事务执行契约**：
- 同聊天 / 同 scope 校验；
- 写入前快照；
- 写入后重新读取验证；
- 只有验证成功才把冷档案标记为 restored；
- 验证失败时回滚；
- 聊天切换时中止；
- 单次最多处理一条；
- 自动路径绝不弹 `confirm()`。

等事务契约和离线测试完成，再考虑把它接到正式 VAB 核心；目前生产启动链不执行任何 Rehydration 写操作。
